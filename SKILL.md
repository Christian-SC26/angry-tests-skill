# Angry Tests — принципы Егора Бугаенко

«Angry Tests» — книга Егора Бугаенко (@yegor256) об автоматическом тестировании.
Том 1 вышел в апреле 2025 года: около 159 коротких рекомендаций, каждая примерно на страницу, с примерами на Java, C++, Go, Python, Ruby и JavaScript.
Том 2 вышел в мае 2026 года. Он расширяет тему другими видами тестов и тестированием с помощью ИИ и вводит понятие «Headless Angry Tests».

Этот скилл построен на опубликованных автором выдержках из книги (репозиторий
[yegor256/at](https://github.com/yegor256/at), главы 2, 3 и 6, номера правил сохранены)
и на его блоге, где многие идеи разобраны подробно. Формулировки правил взяты из выдержек.
Пояснения, примеры и способы разрешить противоречия добавлены нами; их там, где это существенно, помечаем как интерпретацию.
Главы 1, 4, 5 и содержимое второго тома публично не выложены. Не выдумывай их содержание и не ссылайся на «правила» с номерами, которых нет ниже.

Справочные файлы (читай по необходимости):
- `references/fancy-tests.md` — глава 6: «модные» виды тестов и инструменты по экосистемам.
- `references/anti-patterns.md` — 23 антипаттерна юнит-тестирования из блога Бугаенко и правила, которые их лечат.
- `references/layout.md` — раскладка и именование тестовых файлов, `*Test` и `*ITCase`, куда класть фейки.

## 0. Философия: почему тесты «злые»

1. **Тест — охотник за багами, а не демонстрация того, что код работает.** Хороший тест
   пытается сломать код: граничные значения, мусорный ввод, юникод, пустоты, огромные объёмы,
   параллельность, медленная или «враждебная» среда. Тест, который проверяет только happy path,
   «мягкий» и почти бесполезен (правила 3.5, 2.17, 3.9).
2. **Тест — документация, которая не врёт.** Имя теста — предложение о поведении объекта,
   failure message — объяснение, что сломалось. Комментарии не нужны (2.14, 2.9, 2.15).
3. **Тест проверяет контракт, а не реализацию.** Только публичный интерфейс, без рефлексии,
   без приватных методов, без `verify()` над внутренними вызовами (2.13, 2.16, 2.20, 3.27).
4. **Тесты давят на дизайн.** Если тест трудно написать коротко, значит, плох дизайн
   объекта, а не тест: изменяемое состояние, статика, скрытые зависимости, «божественные» объекты.
   Однооператорные тесты толкают код к неизменяемым объектам (2.30).
5. **Плохой тест лучше никакого** (2.32), а **каждое изменение кода приносит новые тесты** (2.33).
   Совершенство тестов — не повод их не писать.
6. **Красный тест не прощают.** Нельзя подгонять ожидание под баг. Тест либо зелёный честно,
   либо отключён с объяснением (2.29, 2.19).

## 1. Как применять скилл

### Когда пишешь новые тесты
1. Определи контракт объекта: что он обещает (документация, сигнатуры, типы). Тестируй только это.
2. Составь список «болевых точек»: где этот код вероятнее всего сломается (границы, пустые
   и огромные входы, юникод, null/None, конкурентный доступ, ошибки I/O, таймауты).
3. На каждую точку — отдельный тест: имя-предложение, свои уникальные «нерегулярные» данные,
   одна проверка с failure message, без общих полей и `setUp`.
4. Зависимости — через фейки (настоящие простые реализации интерфейсов), файловая система —
   настоящая во временной директории, сеть — только локальная на эфемерных портах.
5. Проставь таймауты, теги (fast/deep), убедись, что тест не пишет в лог и проходит без интернета.
6. Проверь тест чеклистом из раздела 5.

### Когда ревьюишь тесты
Для каждого нарушения выдай: файл:строка → номер правила → в чём проблема → как исправить
(с кодом). Группируй по серьёзности:
- **Критично** — тест ничего не проверяет или врёт: нет assert (2.3), проглоченные исключения
  (3.25), `assertDoesNotThrow` (2.5), подгонка ожидания под баг (2.29), зависимость от порядка
  или общих данных (2.10, 2.11), обращение к сети (3.23), бесконечное ожидание (3.14), `sleep` (3.15).
- **Важно** — моки и `verify` (2.28, 3.27), рефлексия и приватные методы (2.13, 2.20),
  нет failure messages (2.9), проверка логов и деталей ошибок (2.24, 3.24, 3.37), только happy path (3.5).
- **Стиль** — длина (2.1), имена (2.14), комментарии (2.15), «foo»-данные (2.7),
  инлайн-литералы (2.12), сокращённые флаги (3.30).

Не переписывай тесты массово без запроса: сначала отчёт, потом правки. Дублирование кода
в тестах — последняя по важности проблема (3.48); не начинай с неё.

## 2. Глава 2. Basics — подробно

### 2.1 Каждый тест короче дюжины строк
Если тест длиннее 12 строк, он делает подготовку, которую должен делать фейк, фикстура-объект
или матчер. Длинная подготовка — признак плохого дизайна тестируемого объекта (слишком много
зависимостей, изменяемое состояние).

### 2.2 Одна проверка на тест
Один тест — одно утверждение о поведении. Когда в тесте пять `assert`, первый упавший скрывает
остальные, а имя теста не может описать все пять утверждений. Нужно проверить пять вещей —
пиши пять тестов. Сложную проверку одного факта собирай матчером (`allOf`, кастомный матчер),
а не цепочкой assert'ов.
> Связь с 2.23/2.25 (интерпретация): «одна проверка» относится к утверждению, ради которого
> написан тест. Если тест вынужденно проходит многошаговый сценарий, промежуточные результаты
> тоже проверяются (см. ниже), но такие тесты — исключение и обычно относятся к «deep».

### 2.3 Assert в каждом тесте
Тест без проверки («вызвали — не упало») — антипаттерн *Secret Catcher* / *Line Hitter*:
он раздувает покрытие и ничего не ловит. Даже если важно лишь «не упало», проверь результат.

### 2.4 Завершай каждый тест проверкой
Последний оператор теста — assert. Действия после него либо лишние, либо скрыто влияют на
другие тесты (уборка — см. 2.27), либо означают, что проверка стоит не там.

### 2.5 Не используй `assertDoesNotThrow`
Это проверка, которая ничего не утверждает о результате. Замени её проверкой того, что
вернул или как изменился объект. Исключение и так уронит тест.
```java
// плохо
assertDoesNotThrow(() -> new Report(data).save(path));
// хорошо
new Report(data).save(path);
MatcherAssert.assertThat("report file must be non-empty", Files.size(path), Matchers.greaterThan(0L));
```

### 2.6 Не вызывай `fail()` явно
`try { x(); fail(); } catch (E e) {}` — устаревшая идиома с ловушками (проглоченные исключения,
широкий catch). Используй `assertThrows` или матчеры (`Assertions.assertThrows(...)`,
`pytest.raises`, `expect(...).toThrow()`).

### 2.7 Нерегулярные входные значения вместо `"foo"`
`"foo"`, `"test"`, `1`, `42` — удобные значения, на которых код почти никогда не ломается.
Бери данные, которые провоцируют баги: юникод и эмодзи, пробелы по краям, кавычки и спецсимволы,
`\n`, `\t`, `\0`, очень длинные строки, отрицательные числа, `Integer.MAX_VALUE`, пустые коллекции.
```java
final String name = "Жан-Пьер  O'Нил 😀\t";
```

### 2.8 Разные входные данные в каждом тесте
Не переиспользуй одни и те же значения между тестами: каждый тест — новая попытка найти баг,
и одинаковые данные сужают пространство поиска. Отсюда же 2.11 (никаких общих констант)
и 3.8 (рандомизаторы).

### 2.9 Всегда пиши failure messages
Сообщение — первое, что видит программист при падении, обычно в CI-логе без IDE.
Оно описывает ожидаемое поведение, а не повторяет код:
```java
MatcherAssert.assertThat(
    "counts only non-empty greetings, ignoring blank lines",
    new Greetings(text).count(),
    Matchers.equalTo(3)
);
```
Python: `assert_that(actual, equal_to(3), "counts only non-empty greetings")` (PyHamcrest)
или `assert actual == 3, "counts only non-empty greetings"`. JS: `expect(x, 'message')`
(chai) или `assertThat('message', x, equalTo(3))` (hamjest). Go: `t.Errorf("counts only ...: got %d", n)`.
Rust: `assert_eq!(n, 3, "counts only non-empty greetings")`.

### 2.10 Никаких общих данных между тестами; никаких `setUp`/`tearDown`
Каждый тест самодостаточен: читается сверху вниз без прыжков в `@BeforeEach`, поля класса
и фикстуры. Общее состояние делает тесты зависимыми от порядка (антипаттерн *Generous Leftovers*)
и прячет подготовку от читателя. В тестовом классе нет полей, только тестовые методы.
Запрещено: `@Before/@BeforeEach/@After/@AfterEach/@BeforeAll`, `setUp/tearDown` в unittest,
`beforeEach/afterEach` в Jest/Mocha, общие изменяемые pytest-фикстуры уровня module/session.
Нужна общая подготовка — вынеси её в фейк-объект или фикстура-объект (3.46), который каждый
тест создаёт сам.

### 2.11 Не объявляй констант (статических литералов) в тестах
`private static final String NAME = "Jeff";` в тестовом классе — общее состояние в замаскированном
виде: тесты начинают использовать одни данные (нарушение 2.8), а связь между тестами становится
неявной. Каждый тест объявляет свои данные локально.

### 2.12 Не инлайнь константы — сначала присваивай переменной
Литерал, который нужен и на входе, и в ожидании, живёт в одной локальной переменной. Тогда
видно, что ожидаемое значение вытекает из входа, и нет двух «магических» копий, которые разойдутся.
```java
// плохо
assertThat("greets", new Greeting("Анна").text(), containsString("Анна"));
// хорошо
final String name = "Анна-Мария Ö";
assertThat("greeting must mention the name", new Greeting(name).text(), containsString(name));
```
> Это не противоречит 2.30: «один оператор» — цель для логики теста; объявления данных
> перед ним допустимы.

### 2.13 Не обходи интерфейсы объектов, особенно рефлексией
Никакого чтения приватных полей, `setAccessible(true)`, `Whitebox`, `obj._private`,
`instance_variable_get`, monkey-patching внутренностей. Тест, нарушающий инкапсуляцию,
ломается при любом рефакторинге (*Anal Probe*, *Inspector*). Если поведение нельзя проверить
через интерфейс, его либо нет в контракте, либо у объекта не хватает метода — и это проблема дизайна.

### 2.14 Имена тестов — полные английские предложения, начинающиеся с глагола
`buildsHtmlPage`, `rejectsNegativeAmount`, `readsFileWithUnicodeName`. Подлежащее — имя класса:
«`HtmlPage` builds html page». Без префиксов `test`, `should`, без номеров (`test1` —
антипаттерн *Enumerator*). Python: `test_builds_html_page` (префикс `test_` требует раннер,
дальше — предложение). Go: `TestBuildsHtmlPage`. Rust: `builds_html_page`.
JS: `it('builds HTML page', ...)`.

### 2.15 Никаких комментариев в тестах и вокруг них
Если тест нуждается в комментарии, он неясен: перепиши его, улучши имя и failure message.
Комментарии устаревают; имя и сообщение проверяются при каждом запуске.

### 2.16 Не проверяй поведение, не обещанное контрактом
Порядок элементов в `HashSet`, точный текст `toString()`, формат сообщения исключения,
количество внутренних вызовов, тайминги — всё это детали. Тест на них ломается от безопасных
изменений и учит команду игнорировать красные тесты (*Nitpicker*, *Sequencer*).

### 2.17 Проверяй самые уязвимые места
Сначала тестируй то, где баг наиболее вероятен и наиболее дорог: границы, переполнение,
пустые и огромные входы, кодировки, конкурентность, ошибки внешних ресурсов. Проверки
очевидного раздувают набор и почти ничего не ловят.

### 2.18 Не тестируй геттеры, сеттеры и подобную примитивную функциональность
Тривиальный код не ломается. Его покрывают тесты настоящего поведения. (В духе Бугаенко
геттеров и сеттеров вообще лучше не иметь, но это уже вопрос дизайна.)

### 2.19 Не удаляй тесты — отключай
Удалённый тест уносит знание о сценарии и баге. Отключённый (`@Disabled("…")`,
`@pytest.mark.skip(reason=…)`, `it.skip`, `#[ignore = "…"]`, `t.Skip("…")`) остаётся видимым
напоминанием и легко возвращается. Причина и ссылка на тикет обязательны.

### 2.20 Никогда не тестируй private и protected методы
Они — деталь реализации и тестируются через публичный интерфейс. Если приватный метод так
сложен, что его хочется протестировать отдельно, — это отдельный объект, который просится наружу.

### 2.21 Закрывай ресурсы: файлы, сокеты, соединения
`try-with-resources`, `with`, `defer`, `ensure`, `Drop`. Незакрытые ресурсы приводят
к утечкам, плавающим падениям соседних тестов и «занятым» портам.

### 2.22 Не пиши в продакшен-коде функциональность, нужную только тестам
`@VisibleForTesting`, `reset()`, сеттеры «для тестов», флаги `isTestMode`, публичные поля ради
проверки — так тесты портят дизайн. Если тесту чего-то не хватает, сделай это полноценной частью
контракта или пересмотри тест.
> Нюанс (интерпретация по блогу Бугаенко): фейк-объекты, поставляемые вместе с библиотекой
> (`FkUser`, `FakeStorage`), он считает полноценной частью API — ими пользуются и клиенты
> библиотеки в своих тестах. Это не «код только для тестов».

### 2.23 Проверяй каждый шаг на пути к концу сценария
Если тест проходит use case из нескольких шагов, проверяй результат каждого шага, а не только
финальный. Иначе при падении непонятно, на каком шаге всё пошло не так, а ошибка может
замаскироваться на следующих шагах.

### 2.24 Не проверяй побочные эффекты вроде логов
Лог — не контракт. Проверка, что «в лог записалось X», привязывает тест к формулировкам
и не доказывает, что поведение правильное (*Dodger*). См. также 3.37.

### 2.25 Проверяй все возможные промежуточные результаты
Близко к 2.23: если объект возвращает промежуточные значения (статусы, частичные результаты,
идентификаторы), убедись, что они правильные, а не просто «не null».

### 2.26 Не тестируй конструкторы — в них нет кода
По Бугаенко [конструкторы не содержат кода](https://www.yegor256.com/2015/05/07/ctors-must-be-code-free.html):
они только присваивают атрибуты. Тестировать нечего. Если в конструкторе есть логика, исправлять
нужно конструктор: перенести логику в методы, которые вызываются при обращении.

### 2.27 Убирай перед тестом, а не после
Тест готовит себе чистую среду в начале (удаляет и создаёт нужный каталог, очищает таблицу).
Уборка после теста не выполняется, если тест упал или процесс убит, и уничтожает следы,
нужные для отладки (см. 3.36). Лучше всего — уникальная временная директория на тест (3.10).

### 2.28 Не используй мок-фреймворки — пиши фейки
Моки (Mockito, unittest.mock, sinon, gomock) описывают ожидаемые вызовы, то есть реализацию,
а не поведение. Тесты с ними хрупкие, многословные и часто проверяют сами моки (*Mockery*).
[Фейк](https://www.yegor256.com/2014/09/23/built-in-fake-objects.html) — простая, но честная
реализация интерфейса (in-memory хранилище, фиксированные часы, локальный HTTP-сервер).
Фейк пишется один раз, сам тестируется и переиспользуется.
```java
// плохо
final Storage storage = Mockito.mock(Storage.class);
Mockito.when(storage.read("k")).thenReturn("v");
// хорошо
final Storage storage = new FkStorage(new MapOf<>("k", "v"));
```

### 2.29 Не прощай неправильное поведение — отключай тест
Если код ведёт себя неправильно, нельзя менять ожидание под факт («ну пусть пока будет 4 вместо 5»).
Тест с честным ожиданием отключается с указанием бага (2.19), баг заводится. Подгонка ожиданий
превращает тест в *The Liar*.

### 2.30 Стремись к тестам из одного оператора
[Single-statement unit tests](https://www.yegor256.com/2017/05/17/single-statement-unit-tests.html):
тело теста — один `assertThat(...)`, внутри которого объект создаётся и вызывается.
Алгоритмическая подготовка уезжает в объекты и матчеры, которые переиспользуются.
Тесты становятся декларативными, а продакшен-код подталкивается к неизменяемости.
```java
@Test
void countsWordsInUnicodeText() {
    MatcherAssert.assertThat(
        "counts words separated by any whitespace",
        new Words("Привет,\tмир   ёж").count(),
        Matchers.equalTo(3)
    );
}
```

### 2.31 Используй Hamcrest
Матчеры дают читаемые проверки, понятные сообщения об ошибке («Expected: … but: …»),
композицию (`allOf`, `hasItem`, `not`) и возможность писать свои (3.3). Аналоги:
Java — Hamcrest (Бугаенко отдаёт ему предпочтение); Python — PyHamcrest; JS/TS — hamjest;
C++ — gMock matchers в GoogleTest; Go — github.com/corbym/gocrest; Rust — hamcrest2 / googletest-rust;
Ruby — matchers RSpec или minitest с понятными сообщениями; Swift — Nimble.

### 2.32 Плохие тесты лучше, чем никаких
Не бросай писать тест из-за того, что он получается неидеальным. Тест можно улучшить позже,
а отсутствующий тест не ловит ничего. При ревью не требуй переписать всё: отмечай нарушения,
но принимай ценный тест.

### 2.33 Меняешь код — добавляй тесты
Любое изменение, особенно исправление бага, сопровождается новыми тестами. Исправление бага
начинается с теста, который его воспроизводит (3.4, 3.5).

## 3. Глава 3. Advanced — подробно

### 3.1 Делите тесты на «быстрые» (~50 мс) и «глубокие» (интегрирующие всё)
Быстрые тесты запускаются постоянно и на каждой сборке, глубокие (настоящая БД, Docker,
браузер, внешние процессы) — отдельной фазой. Разделение — через теги (3.20) и/или суффиксы
(`*Test` / `*ITCase`, см. `references/layout.md`).

### 3.2 Делайте тесты «нестабильными», а потом ждите баг-репортов и исправлений
(интерпретация) Тесты должны намеренно вносить разнообразие: случайные данные (3.8),
случайный порядок, параллельный запуск (3.33), неудобная среда (3.9). Такой тест иногда падает,
и это не «flaky test, перезапусти», а найденный баг. Падение фиксируется в баг-репорте
и исправляется (см. также 3.41 — исправляется после расследования, а не наугад).

### 3.3 Пишите собственные матчеры и переиспользуйте их
Повторяющаяся проверка («валидный XML с узлом X», «JSON содержит поле Y») становится
матчером с понятным описанием. Это делает возможными тесты из одного оператора (2.30)
и даёт хорошие failure messages.
```java
MatcherAssert.assertThat("renders a valid page", page, new IsValidHtml());
```

### 3.4 Воспроизводи баги с минимальной обвязкой
Тест на баг — минимальный вход и минимум объектов, достаточных для падения. Без поднятия
всего приложения, если баг воспроизводится на одном объекте.

### 3.5 Тесты воспроизводят конкретные баги, а не успешные сценарии
Цель теста — показать, что конкретная поломка невозможна. Перед тестом спроси «какой баг
здесь может быть?» и напиши тест, который его поймал бы. Набор из одних «успешных» сценариев —
антипаттерн *Happy Path*.

### 3.6 Не проверяй неважные детали, не будь педантом без причины
Сравнение всего вывода целиком, когда важна одна часть (*Nitpicker*), делает тесты хрупкими.
Проверяй то, что важно для контракта; остальное — через `containsString`, `hasEntry`, XPath, JSONPath.

### 3.7 Придумай DSL и пиши на нём тестовые истории
Если тестов много и они однотипны, опиши их в декларативном формате (например, YAML-файлы
«история: вход → ожидание»), а один параметризованный тест прогоняет все истории. Новые
кейсы добавляются без кода и читаются не только программистами.

### 3.8 Используй рандомизаторы для генерации тестовых данных
Случайные строки, числа, имена, идентификаторы при каждом запуске расширяют пространство
проверки. Падение должно печатать seed/значения, чтобы его можно было воспроизвести.
Инструменты: Java — `RandomStringUtils`, Instancio, EasyRandom, Datafaker; Python — Faker,
Hypothesis; JS — @faker-js/faker; Go — `math/rand` + `testing/quick`; Rust — `fake`, `proptest`.

### 3.9 Не помогай тестам — создавай им самую неудобную среду
Пробелы и юникод в путях, нестандартная локаль и часовой пояс, read-only каталоги,
случайный порядок тестов, параллельный запуск, медленные ответы фейков, малые лимиты памяти.
Код, переживший такую среду, переживёт и продакшен.

### 3.10 Не храни временные файлы рядом с исходниками — используй временную директорию
`@TempDir`, `tmp_path` (pytest), `t.TempDir()` (Go), `tempfile`, `Dir.mktmpdir`, `tempfile::TempDir`.
Никаких файлов, создаваемых тестом, в `src/` и корне репозитория.

### 3.11 Не тестируй абстрактные классы
Тестируются конкретные реализации. Абстрактный класс сам по себе не имеет поведения,
а его тестирование через анонимную подделку проверяет подделку.

### 3.12 Тесты ничего не пишут в лог — лог пуст
Тест молчит (*Loudmouth*). Никаких `System.out.println`, `print`, `console.log` в тестах.
Шумный вывод скрывает настоящие предупреждения. Логирование продакшен-кода во время тестов
по возможности приглушено конфигурацией.

### 3.13 Параметризуй тесты
Один и тот же контракт на множестве входов — один параметризованный тест (`@ParameterizedTest`,
`@pytest.mark.parametrize`, табличные тесты в Go, `test.each` в Jest, `rstest`).
Каждый набор параметров — отдельный кейс в отчёте.

### 3.14 Останавливай тесты по таймауту, не давай им работать вечно
Каждый тест (особенно с I/O, потоками, сетью) имеет таймаут: `@Timeout`,
`junit.jupiter.execution.timeout.default`, `pytest-timeout`, `jest --testTimeout`,
`go test -timeout`. Зависший тест хуже упавшего: он блокирует CI и ничего не сообщает.

### 3.15 Не спи произвольное число секунд — жди события
`Thread.sleep(1000)` либо замедляет тесты, либо (на медленной машине) делает их плавающими.
Жди условия: `CountDownLatch`, `Future.get`, Awaitility (`await().until(...)`),
опрос с таймаутом, `asyncio.Event`, каналы в Go.

### 3.16 Если нужно имитировать зависание — спи миллиард секунд
Когда фейк должен «зависнуть» (чтобы проверить таймауты вызывающего кода), он спит
заведомо бесконечно (`TimeUnit.SECONDS.sleep(1_000_000_000L)`), а не «подольше» (5 секунд).
Так тест детерминирован: проверяется именно реакция на зависание, а не гонка двух таймеров.

### 3.17 Пусть разные тесты проверяют одну и ту же часть кода
Перекрытие тестов — нормально, это не дублирование. Разные тесты подходят к коду с разных
сторон и ловят разные баги. Не удаляй тест из-за того, что «эта строка уже покрыта».

### 3.18 Тестируй потокобезопасность объектов
Объекты, которые могут использоваться из разных потоков, проверяются конкурентным тестом:
много потоков одновременно вызывают метод, затем проверяется инвариант. Подробности:
[Java](https://www.yegor256.com/2018/03/27/how-to-test-thread-safety.html),
[Ruby](https://www.yegor256.com/2018/11/06/ruby-threads.html).
```java
@Test
void incrementsCounterFromManyThreads() throws Exception {
    final Counter counter = new Counter();
    final int threads = Runtime.getRuntime().availableProcessors() * 4;
    final CountDownLatch start = new CountDownLatch(1);
    final ExecutorService service = Executors.newFixedThreadPool(threads);
    final Collection<Future<?>> futures = new ArrayList<>(threads);
    for (int idx = 0; idx < threads; ++idx) {
        futures.add(service.submit(() -> { start.await(); counter.increment(); return null; }));
    }
    start.countDown();
    for (final Future<?> future : futures) { future.get(1L, TimeUnit.MINUTES); }
    MatcherAssert.assertThat("counts every increment exactly once", counter.value(), Matchers.equalTo(threads));
}
```
(Такой тест длиннее 12 строк — поэтому 3.49 и библиотеки вроде
[yegor256/threads](https://github.com/yegor256/threads) / cactoos `RunsInThreads` сокращают его до одного оператора.)

### 3.19 Пусть тесты повторяют попытку, если тестируемое поведение нестабильно по природе
Если нестабильна сама проверяемая вещь (внешний сервис в живом тесте, сетевая гонка,
вероятностный алгоритм), допустим ретрай (`@RetryingTest` из junit-pioneer, `pytest-rerunfailures`,
`jest.retryTimes`). Это не способ скрыть баг в своём коде (см. 3.41).

### 3.20 Используй теги для классификации тестов
`@Tag("fast")`, `@Tag("deep")`, `@pytest.mark.slow`, build tags в Go, `#[ignore]` + отдельный
прогон в Rust. Теги позволяют запускать нужные подмножества: быстрые локально, глубокие в CI.

### 3.21 Пусть фреймворк повторяет некоторые тесты, чтобы чаще задевать баг
`@RepeatedTest(100)`, `pytest-repeat`, `go test -count=100`. Особенно для конкурентного
кода и тестов с рандомизацией: редкий баг проявляется на сотом повторе.

### 3.22 В тестах на потокобезопасность используй все доступные CPU
Число потоков — от `availableProcessors()` (`os.cpu_count()`, `runtime.NumCPU()`) и больше.
На двух потоках гонки почти не проявляются.

### 3.23 Все тесты проходят без интернета
Отключи сеть и запусти набор: он должен быть зелёным. Внешние сервисы заменяются фейками
или локальными серверами (Testcontainers, локальный HTTP-сервер на эфемерном порту).
Тест, зависящий от интернета, медленный, плавающий и не воспроизводится (*Local Hero*).

### 3.24 Не проверяй детали ошибок
Проверяй тип исключения или факт ошибки, но не текст сообщения: формулировки меняются,
а контрактом не являются (2.16).
```java
Assertions.assertThrows(IllegalArgumentException.class, () -> new Amount(-1));
```

### 3.25 Держи область try/catch минимальной
Широкий `try` ловит исключения не из той строки, а `catch` с пустым телом или общим
`Exception` прячет баги (*Greedy Catcher*). В тестах try/catch почти не нужен:
используй `assertThrows` и пусть непредвиденные исключения роняют тест.

### 3.26 Строго один тестовый файл на один файл продакшен-кода
`Foo.java` ↔ `FooTest.java`, в том же пакете. Тестовый файл без пары в продакшене (или с
непонятным именем) запрещён. Проверяется автоматически:
[jtcop](https://github.com/volodya-lombrozo/jtcop). См. `references/layout.md`.

### 3.27 Не используй `verify()` из мок-фреймворков
`verify(mock).save(x)` проверяет, *как* объект сделал работу, а не *что* получилось. Любой
рефакторинг (кэш, батчинг, другой порядок) ломает тест при правильном поведении. Проверяй
состояние фейка после действия: `assertThat(storage.read("k"), equalTo("v"))`.

### 3.28 Не используй PowerMock и подобные фреймворки
Подмена статики, конструкторов и финальных классов через манипуляции байткодом —
симптом плохого дизайна (статические зависимости, `new` внутри логики). Лечи дизайн:
инъекция зависимостей через конструктор, интерфейсы, фейки.

### 3.29 Не создавай объекты и не вызывай методы с аргументами по умолчанию
В тестах передавай все аргументы явно. Иначе тест неявно зависит от значений по умолчанию:
они меняются — тест меняет смысл, не меняя кода. Явные аргументы документируют, что
именно проверяется.

### 3.30 Не сокращай: `curl --silent`, а не `curl -s`
В тестовых скриптах, CI-конфигурациях и командах — длинные формы флагов. Читателю не нужно
вспоминать, что значит `-s` у конкретной утилиты.

### 3.31 Не позволяй продакшен-объектам делать работу тестов — проверяй входы и состояние
(интерпретация) Тест сам проверяет то, что важно: не полагайся на то, что продакшен-код
«где-то внутри» бросит исключение при неверных данных или сам проверит своё состояние.
Тест явно проверяет, что входы приняты и состояние после действия правильное.

### 3.32 Используй декорирующие инварианты, чтобы ловить неправильное использование объектов в тестах
Оберни зависимость в декоратор, который во время теста проверяет правила использования:
ресурс закрыт ровно один раз, метод не вызывается после `close()`, нет вызовов из чужого
потока, входы не null. Декоратор кидает исключение при нарушении — и тест падает в точке
ошибки, без моков и `verify`.
```java
final Input input = new StrictInput(new InputOf(file)); // падает при повторном close() или чтении после close()
```

### 3.33 Запускай тесты в параллельных потоках
Включи параллельное исполнение (`junit.jupiter.execution.parallel.enabled=true`,
`pytest -n auto` / pytest-xdist, `t.Parallel()`, Jest workers, cargo test по умолчанию).
Это ускоряет набор и выявляет скрытое общее состояние между тестами.

### 3.34 Каждый быстрый тест — меньше 100 миллисекунд
Жёсткая граница для «быстрых» (цель — около 50 мс, см. 3.1). Медленный «быстрый» тест
переносится в deep или переписывается (*Slow Poke*).

### 3.35 Не мокай файловую систему
Используй настоящую ФС во временной директории (3.10). Мок ФС проверяет мок, а баги
(права, кодировки имён, симлинки, пробелы в путях) живут в настоящей ФС.

### 3.36 Временные файлы доступны после окончания набора тестов
Создавай их в известном месте внутри каталога сборки (`target/`, `build/`), а не в системном
`/tmp`, который тут же удалится, — чтобы после падения в CI можно было посмотреть, что
оставил тест. Инструмент: [yegor256/mktmp](https://github.com/yegor256/mktmp). Сочетается с 2.27:
уборка — перед тестом.

### 3.37 Не проверяй содержимое логов, которые пишет продакшен-код
Дополняет 2.24: перехват логгера и проверка строк в нём делает тест зависимым от формулировок
и уровней логирования. Проверяй наблюдаемое поведение.

### 3.38 Используй эфемерные TCP-порты
Никаких захардкоженных `8080`: параллельные тесты и другие процессы конфликтуют.
Бери свободный порт у ОС (`new ServerSocket(0)`, `bind(('', 0))`, `:0` в Go, `port: 0` в Node).

### 3.39 Не используй наследование для переиспользования тестовых инструментов
Никаких `AbstractDatabaseTest`, от которых наследуются тестовые классы: это неявное общее
состояние и хрупкая иерархия. Переиспользование — через композицию: фейки, матчеры,
фикстура-объекты, JUnit-расширения, тестовые библиотеки (3.49).

### 3.40 Не бойся длинных тестовых классов — это нормально
Тестовый класс — набор независимых сценариев, а не объект с поведением. 5000 строк в тестовом
классе — не проблема. Не дроби тестовый класс искусственно (это нарушит и 3.26).

### 3.41 Не исправляй продакшен-код в ответ на плавающее падение теста
Плавающий тест сначала исследуют: воспроизводят детерминированно (3.4, повторами 3.21),
находят причину — в тесте, среде или коде. Правка кода «наугад» под нестабильный тест
маскирует настоящую причину.

### 3.42 Используй maybeslow или подобную библиотеку для диагностики долгих тестов
[yegor256/maybeslow](https://github.com/yegor256/maybeslow) сообщает, какой тест долго
выполняется, пока он ещё идёт. Аналоги: `pytest --durations=20`, `go test -v` + `-timeout`,
`jest --detectOpenHandles`, отчёты о длительности в Surefire.

### 3.43 Убивай долгие тесты по таймауту
Таймаут не только на тест (3.14), но и на весь набор в CI (`timeout-minutes` в GitHub Actions,
`forkedProcessExitTimeoutInSeconds` в Surefire). Процесс, повисший навсегда, обязан быть убит.

### 3.44 Инлайнь фикстуры вместо отдельных файлов
Небольшие входные данные (JSON, XML, CSV на десяток строк) пишутся прямо в тесте
(text blocks, многострочные строки). Читатель видит вход и ожидание в одном месте
и не прыгает по файлам `src/test/resources`.

### 3.45 Не храни большие фикстуры в статических файлах — пусть тесты их генерируют
Мегабайтный файл в репозитории непрозрачен и не показывает, что в нём важно. Большие данные
генерируются кодом: миллион строк, глубокая вложенность, огромный файл.

### 3.46 Создавай фикстура-объекты, генерирующие большие фикстуры в рантайме
Генерацию из 3.45 оформляй объектами: `new LargeCsv(rows, columns)`, `new DeepJson(depth)`.
Они переиспользуются, тестируются и делают тест одним оператором.

### 3.47 Эталонные фикстуры храни статическими файлами в репозитории
Исключение из 3.44/3.45: реальные образцы, которые нельзя или бессмысленно генерировать
(настоящие файлы клиентов, ответы чужих API, «золотые» выходные данные, файлы, сломавшие
продакшен). Они хранятся как есть, и тесты прогоняют их все.

### 3.48 Дублирование кода в тестах — последняя проблема, которую стоит исправлять
Тесты должны быть читаемы по отдельности. Немного повторения лучше, чем общие helper-методы,
поля и базовые классы, которые связывают тесты. DRY в тестах — низший приоритет.

### 3.49 Выделяй тестовые библиотеки
Когда фейки, матчеры и фикстура-объекты становятся полезны нескольким модулям или проектам,
выносятся в отдельную библиотеку (как Бугаенко сделал с threads, mktmp, maybeslow).
Это правильная альтернатива наследованию (3.39) и статическим утилитам.

## 4. Глава 6. Fancy Tests — кратко
Юнит- и интеграционных тестов мало. Сборка должна включать и другие автоматические проверки:
орфографию, property-based тесты, фаззинг, мутационное тестирование, проверку раскладки файлов,
нагрузочные тесты и бенчмарки (с сравнением с прошлой сборкой), линтеры, статический
и динамический анализ, метрики с порогами, тесты SQL, санитайзеры, поиск клонов,
браузерные и кросс-браузерные тесты, облачные анализаторы, живые тесты конфигураций,
health checks после деплоя, генерацию тестов, тесты безопасности, проверку лицензий,
поиск избыточных тестов, проверку архитектуры. Полный список 6.1–6.28 с инструментами
по языкам — в `references/fancy-tests.md`.

## 5. Чеклист для каждого теста

- [ ] Имя — предложение с глаголом, без `test`/`should`/номеров (2.14)
- [ ] ≤ 12 строк, в идеале один оператор (2.1, 2.30)
- [ ] Ровно одна проверка, она последняя (2.2, 2.4), есть failure message (2.9)
- [ ] Нет `assertDoesNotThrow`, `fail()`, широкого try/catch (2.5, 2.6, 3.25)
- [ ] Данные нерегулярные/случайные, свои для этого теста, в локальных переменных (2.7, 2.8, 2.11, 2.12, 3.8)
- [ ] Нет полей класса, `setUp`/`tearDown`, наследования тестовых классов (2.10, 3.39)
- [ ] Только публичный интерфейс; нет рефлексии и приватных методов (2.13, 2.20)
- [ ] Проверяется контракт, а не детали: не логи, не тексты ошибок, не порядок в неупорядоченном (2.16, 2.24, 3.24, 3.37)
- [ ] Фейки вместо моков, нет `verify`, нет PowerMock (2.28, 3.27, 3.28)
- [ ] Настоящая ФС во временной директории, эфемерные порты, нет интернета (3.10, 3.35, 3.38, 3.23)
- [ ] Таймаут есть, `sleep` нет (кроме «миллиарда секунд» в фейке) (3.14, 3.15, 3.16)
- [ ] Ресурсы закрыты, уборка в начале, а не в конце (2.21, 2.27)
- [ ] Тест молчит (3.12); быстрый тест < 100 мс, иначе тег deep (3.1, 3.34, 3.20)
- [ ] Нет комментариев (2.15); все аргументы явные (3.29); длинные флаги в командах (3.30)
- [ ] Тест ловит конкретный баг или уязвимое место, а не повторяет happy path (2.17, 3.5)

Чеклист на уровне проекта:
- [ ] Один тестовый файл на один файл кода, тот же пакет, суффикс `Test`/`ITCase` (3.26)
- [ ] Набор проходит без сети и параллельно (3.23, 3.33)
- [ ] Есть таймауты на тест и на весь прогон в CI (3.14, 3.43)
- [ ] Отключённые тесты содержат причину и ссылку на баг, удалённых нет (2.19, 2.29)
- [ ] Повторяющиеся проверки — кастомные матчеры, повторяющаяся подготовка — фейки и фикстура-объекты (3.3, 3.46)
- [ ] В сборке есть линтеры, статический анализ и мутационное тестирование (6.4, 6.9, 6.10)

## 6. Полный пример: до и после

До (типичный тест, много нарушений):
```java
public class UserServiceTest {
    private static final String NAME = "foo";            // 2.11, 2.7
    private UserService service;
    private UserRepository repo;

    @BeforeEach                                           // 2.10
    public void setUp() {
        repo = Mockito.mock(UserRepository.class);        // 2.28
        service = new UserService(repo);
    }

    @Test
    public void testCreate() {                            // 2.14
        // create user                                     // 2.15
        User u = service.create(NAME);
        assertNotNull(u);                                 // 2.2, 2.9
        assertEquals("foo", u.name());                    // 2.12
        Mockito.verify(repo).save(Mockito.any());         // 3.27
        System.out.println("created " + u);               // 3.12
    }
}
```

После:
```java
final class UsersTest {
    @Test
    void storesCreatedUserWithUnicodeName() {
        final String name = "Ёжик Ö'Brien 🦔";
        final Users users = new Users(new FkStorage());
        MatcherAssert.assertThat(
            "finds the created user by its exact unicode name",
            users.create(name).id(),
            Matchers.equalTo(users.byName(name).id())
        );
    }

    @Test
    void rejectsBlankName() {
        Assertions.assertThrows(
            IllegalArgumentException.class,
            () -> new Users(new FkStorage()).create(" \t\n"),
            "refuses a name made of whitespace only"
        );
    }
}
```

Тот же стиль на Python (pytest + PyHamcrest):
```python
from hamcrest import assert_that, equal_to

def test_stores_created_user_with_unicode_name():
    name = "Ёжик Ö'Brien 🦔"
    users = Users(FakeStorage())
    assert_that(users.create(name).id, equal_to(users.by_name(name).id), "finds the created user by its exact unicode name")

def test_rejects_blank_name():
    with pytest.raises(ValueError):
        Users(FakeStorage()).create(" \t\n")
```
